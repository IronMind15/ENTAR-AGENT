# 企业级 RAG 知识库系统 — 产品需求文档（PRD）

> 版本：v1.0
> 日期：2026-08-07
> 状态：初稿 / 待评审

---

## 1. 项目概述

### 1.1 背景

企业内部积累了大量文档资产（规章制度、产品手册、合同、技术文档、会议纪要、客服话术等），员工查找信息效率低、知识传承困难。传统的关键词搜索无法理解语义，难以满足"所问即所得"的知识获取需求。

### 1.2 目标

构建一套**基于检索增强生成（RAG）的企业知识库系统**，实现：

- 企业多格式文档的自动化解析、切块、向量化入库
- 基于语义理解的智能问答，答案附带原文引用溯源
- 支持私有化部署，数据不出域
- 可扩展至多租户、多知识库、多场景（内部问答、客服辅助、文档摘要等）

### 1.3 核心用户

| 角色 | 诉求 |
|------|------|
| 普通员工 | 快速查询企业制度、流程、产品信息 |
| 管理者 | 了解系统使用情况、知识覆盖率 |
| 知识库管理员 | 上传/维护文档、管理权限、审核内容 |
| 系统管理员 | 部署运维、监控、模型管理 |

## 2. 系统架构

### 2.1 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                      应用层 (Frontend)                       │
│   Web 端 / 企业微信 / 钉钉 / 飞书 / API 开放接口            │
└──────────────────────┬──────────────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────────────┐
│                    业务服务层 (Backend)                       │
│  对话管理 │ 知识库管理 │ 权限管理 │ 审计日志 │ 应用配置       │
└──────────────────────┬──────────────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────────────┐
│                      RAG 核心引擎                            │
│  Query 改写 → 混合检索 → Rerank → 上下文组装 → LLM 生成     │
└────────┬─────────┬─────────┬─────────┬─────────────────────┘
         │         │         │         │
    ┌────▼───┐ ┌───▼────┐ ┌─▼──────┐ ┌▼──────────┐
    │向量数据库│ │元数据库 │ │对象存储 │ │Embedding  │
    │(Milvus) │ │(PG/SQL)│ │(MinIO) │ │Rerank 服务 │
    └────────┘ └────────┘ └────────┘ └───────────┘
```

### 2.2 数据流

```
文档上传 → 解析 → 分块 → 向量化 → 存入向量库 + 元数据库
                                        ↓
用户提问 → Query 改写 → 向量检索 + BM25 → RRF 融合 → Rerank
                                        ↓
                              Top-K 上下文 + 原始 Query
                                        ↓
                              Prompt 组装 → LLM 生成
                                        ↓
                          返回答案 + 引用来源 + 置信度
```

## 3. 功能模块需求

### 3.1 模块一：文档采集与解析

#### 3.1.1 支持的文档格式

| 类型 | 格式 | 优先级 |
|------|------|--------|
| 文档类 | PDF、DOCX、DOC、PPTX、PPT、TXT、Markdown | P0 |
| 表格类 | XLSX、XLS、CSV | P0 |
| 图片类 | JPG、PNG、扫描件 PDF（需 OCR） | P1 |
| 网页类 | HTML、URL 爬取 | P1 |
| 其他 | 邮件（EML）、思维导图、Notion/飞书文档导入 | P2 |

#### 3.1.2 解析要求

- **PDF 解析**：
  - 原生 PDF：提取文本、表格、图片、保留标题层级
  - 扫描件 PDF：调用 OCR 识别文字，支持中英文混合
  - 保留段落结构、页码信息、表格结构
- **Office 解析**：
  - Word：按段落、标题层级切分，提取嵌入图片
  - Excel：按 Sheet 为单位，每个 Sheet 转为结构化文本或 Markdown 表格
  - PPT：按 Slide 为单位，提取标题+正文+备注
- **OCR 要求**：
  - 中文识别准确率 ≥ 95%
  - 支持表格识别（有线表、无线表）
  - 支持版面分析（区分标题、正文、页眉页脚、图片、表格）

#### 3.1.3 技术选型建议

| 功能 | 推荐工具 | 备选 |
|------|---------|------|
| 通用文档解析 | MinerU / Unstructured / Docling | LlamaParse（API） |
| OCR | PaddleOCR（PP-OCRv4） | Surya、Tesseract |
| 版面分析 | PP-StructureV2 | LayoutLMv3 |
| 表格提取 | Camelot / pdfplumber | Excel 直接解析 |

### 3.2 模块二：文本分块（Chunking）

#### 3.2.1 分块策略

系统需支持以下分块策略，管理员可按知识库配置：

| 策略 | 适用场景 | 参数 |
|------|---------|------|
| 递归字符切分 | 通用文本 | chunk_size=1000, overlap=200 |
| 按标题层级切分 | Markdown、Word | 按 H1→H2→H3 递进 |
| 按段落切分 | 结构化文档 | 段落为最小单元 |
| 语义切分 | 长文本 | 基于相邻句子 embedding 相似度 |
| 父-子分块 | 高精度场景 | 子 chunk（256 token）检索，返回父 chunk（1024 token） |

#### 3.2.2 分块要求

- 每个 chunk 大小默认 512~1024 token，可配置
- 相邻 chunk 需有 10%~20% 重叠（overlap），避免语义截断
- 每个 chunk 必须保留元数据（metadata）：
  - 文档 ID、文档名称
  - 页码 / Sheet 名 / Slide 编号
  - 章节标题路径（如 "第三章 > 3.1 节 > 3.1.2 小节"）
  - 分块索引
  - 创建时间、更新时间

#### 3.2.3 技术选型建议

| 工具 | 说明 |
|------|------|
| LlamaIndex NodeParser | 支持 Hierarchical、Sentence、Markdown、Semantic 等多种策略 |
| LangChain TextSplitters | RecursiveCharacterTextSplitter、MarkdownHeaderTextSplitter |
| Chonkie | 轻量快速的分块库 |

### 3.3 模块三：向量化（Embedding）

#### 3.3.1 模型选型

| 模型 | 维度 | 部署方式 | 说明 |
|------|------|---------|------|
| BGE-M3（推荐） | 1024 | 本地 | 多语言，支持稠密/稀疏/ColBERT 三种表示 |
| GTE-Qwen2 | 768/1536 | 本地 | 阿里出品，中文效果优秀 |
| bge-large-zh-v1.5 | 1024 | 本地 | 中文经典模型 |
| text-embedding-3-small（OpenAI） | 1536 | API | 备选，适合数据可出境场景 |

#### 3.3.2 部署要求

- Embedding 模型需独立部署为推理服务，提供兼容 OpenAI 格式的 API
- 单次请求支持 batch 处理（批量向量化），batch size 可配置
- 推理延迟 P99 < 200ms（单条 512 token 文本）
- 支持 GPU 加速（CUDA）

#### 3.3.3 技术选型建议

| 工具 | 说明 |
|------|------|
| Xinference | 一键部署 Embedding 模型，兼容 OpenAI API |
| TEI（HuggingFace） | Rust 实现的高性能 Embedding 服务 |
| Sentence-Transformers | Python 直接调用，适合开发调试 |
| FlagEmbedding | BAAI 官方，支持微调 |

### 3.4 模块四：向量数据库与存储

#### 3.4.1 向量数据库

**推荐：Milvus（首选）/ Qdrant / Elasticsearch 8+**

需支持：

| 功能 | 要求 |
|------|------|
| 索引算法 | HNSW（默认）、IVF_FLAT |
| 距离度量 | Cosine Similarity（默认）、L2、IP |
| 混合检索 | 向量检索 + 标量过滤（元数据过滤） |
| 全文检索 | 内置 BM25 或集成 Elasticsearch |
| 分区 | 支持按知识库 / 租户分区（Partition Key） |
| 容量 | 单实例支持千万级向量 |
| 高可用 | 多副本、自动故障转移 |

#### 3.4.2 元数据库

**推荐：PostgreSQL（首选）/ MySQL**

存储内容：
- 知识库信息（名称、描述、配置）
- 文档元信息（名称、大小、格式、状态、上传者、权限）
- 分块元数据（chunk_id、文档 id、页码、标题路径、原文内容）
- 对话记录（会话 id、问题、答案、引用 chunk ids、耗时、用户反馈）
- 用户与权限
- 操作审计日志

#### 3.4.3 对象存储

**推荐：MinIO（私有化）/ 阿里云 OSS / AWS S3**

存储内容：
- 原始文档文件
- 解析后的中间产物（如 Markdown 文本）
- 图片、附件

### 3.5 模块五：检索与重排序

#### 3.5.1 混合检索

系统需实现**双路召回 + 融合**：

```
用户 Query
    ├──→ Embedding → 向量检索（语义） → Top 50
    └──→ BM25 → 关键词检索（精确） → Top 50
                        ↓
                RRF（Reciprocal Rank Fusion）融合
                        ↓
                  去重 + 元数据过滤
                        ↓
                  Top 20 → Rerank
                        ↓
                  Top 5 → 送入 LLM
```

- **RRF 公式**：`score = Σ 1/(k + rank_i)`，k 默认 60
- **元数据过滤**：按知识库 ID、文档类型、时间范围、权限进行过滤

#### 3.5.2 Rerank 重排序

| 模型 | 部署 | 说明 |
|------|------|------|
| bge-reranker-v2-m3（推荐） | 本地 | 多语言，精度高 |
| Cohere Rerank 3.5 | API | 效果好，支持多语言 |
| Jina Reranker v2 | 本地/API | 支持 late interaction |

要求：
- Rerank 延迟 P99 < 500ms（20 条候选）
- 支持 batch 打分

#### 3.5.3 Query 改写（可选增强）

| 策略 | 说明 |
|------|------|
| HyDE | 让 LLM 根据问题生成假设答案，用假设答案做检索 |
| Multi-Query | 将原始问题改写为 3~5 个不同角度的子查询，分别检索后合并 |
| Step-back | 让 LLM 先回答一个更抽象的问题，辅助检索 |

### 3.6 模块六：LLM 生成

#### 3.6.1 模型支持

系统需支持多种 LLM 接入，可配置切换：

| 类型 | 模型 | 说明 |
|------|------|------|
| 私有化（推荐） | Qwen2.5-72B / DeepSeek-V3 / GLM-4-9B | 数据不出域 |
| API 调用 | 通义千问、DeepSeek API、Kimi、OpenAI | 灵活切换 |
| 本地小模型 | Qwen2.5-7B / GLM-4-9B（Ollama） | 资源有限场景 |

#### 3.6.2 Prompt 工程

系统 Prompt 模板（需支持后台配置修改）：

```
你是一个企业知识库助手。请根据以下检索到的参考资料回答用户问题。

规则：
1. 只基于参考资料回答，不要编造信息
2. 如果参考资料中没有相关信息，明确告知用户"根据现有资料无法回答"
3. 回答时标注引用来源，格式：[文档名-页码]
4. 回答要准确、简洁、有条理

参考资料：
{context}

用户问题：{query}
```

#### 3.6.3 生成要求

- 支持流式输出（SSE）
- 支持多轮对话（上下文窗口管理）
- 答案需附带引用来源列表（chunk_id、文档名、页码、相关原文片段）
- 支持"答案不满意"反馈，用于后续优化
- Token 消耗需记录到审计日志

#### 3.6.4 部署工具

| 工具 | 说明 |
|------|------|
| vLLM | 高性能 LLM 推理引擎，支持 PagedAttention |
| Ollama | 本地一键部署开源模型 |
| Xinference | 统一模型服务平台 |
| SGLang | 高性能推理框架 |

### 3.7 模块七：知识库管理

#### 3.7.1 知识库 CRUD

- 创建知识库：名称、描述、Embedding 模型、分块策略、关联 LLM
- 编辑 / 删除知识库
- 知识库导入 / 导出
- 知识库克隆

#### 3.7.2 文档管理

- 上传文档（单文件 / 批量 / 文件夹）
- 查看文档列表（名称、格式、大小、状态、上传时间）
- 文档处理状态：待解析 → 解析中 → 切块中 → 向量化中 → 已完成 / 失败
- 文档预览（查看原文、查看分块结果）
- 文档删除（软删除，支持恢复）
- 文档重新解析（修改解析配置后重新处理）

#### 3.7.3 分块调试

- 管理员可在线调试分块效果：选择文档 → 配置分块参数 → 预览分块结果
- 支持手动修改 / 删除 / 新增 chunk

### 3.8 模块八：权限与安全

#### 3.8.1 权限模型

| 层级 | 权限点 |
|------|--------|
| 知识库 | 可见范围（全员 / 部门 / 指定用户） |
| 文档 | 文档级权限（仅上传者可见 / 指定人可见） |
| 检索 | 检索时根据用户权限过滤 chunk（行级过滤） |

#### 3.8.2 安全要求

- 用户认证：对接企业 AD/LDAP / OAuth2 / SSO
- 数据传输 HTTPS 加密
- 敏感信息脱敏（如身份证号、手机号在日志中脱敏）
- 操作审计日志（谁在什么时间上传/删除/查询了什么）
- 数据备份：向量库 + 元数据库定时备份

## 7. 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 文档解析质量差 | 检索准确率低 | 多工具对比测试，人工抽检，建立解析质量评估集 |
| 中文分块语义被截断 | 召回不全 | 使用语义分块 + Parent-Child 策略 + 适当 overlap |
| Embedding 模型领域适配差 | 排序不准 | 收集领域数据微调 BGE-M3 |
| LLM 幻觉 | 给出错误答案 | 严格 Prompt 约束 + 引用溯源 + 置信度阈值 |
| GPU 资源不足 | 推理慢 | 量化部署（AWQ/GPTQ）+ 模型蒸馏 + 缓存 |
| 数据安全合规 | 泄露风险 | 私有化部署 + 权限控制 + 审计日志 |

---

## 8. 验收标准

1. 上传 100 份企业文档（PDF/Word/Excel 混合），系统可正确解析并入库
2. 准备 50 个测试问题（含简单事实、跨文档推理、数值类），答案准确率 ≥ 80%
3. 端到端响应 P95 < 5s（50 并发下）
4. 引用来源准确率 ≥ 90%（答案中引用的原文确实支撑答案）
5. 权限过滤 100% 生效（用户无法检索到无权文档的内容）
