> 关联文档：[恩特小助手_看板功能方法论.md](./恩特小助手_看板功能方法论.md)（千问办公实测教学文件，2026-08-10 已实测跑通看板推送）
> 升级目标：**v1.11.0**（新功能 → minor 升级）

## 1. 背景与目标

### 1.1 背景

千问办公已通过钉钉连接器实测跑通「每日项目看板自动推送」完整链路（2026-08-10），形成方法论文档。恩特小助手当前**不具备**钉钉在线文档/表格读取能力，也**没有**定时主动推送能力，需要将看板功能集成到恩特小助手。

### 1.2 目标

1. **看板技能化**：把看板功能做成一个技能，纳入现有技能体系（`skills/`），支持用户触发 / 定时触发 / 主动提醒三种进入方式。
2. **钉钉文档接入**（本次核心新能力）：识别并读取钉钉在线文档/表格（AI表格 / .axls 在线表格 / 普通文档），作为看板数据源，无需用户导出文件。
3. **每日定时推送**：订阅制、直接按用户需求执行（不反问确认），通过机器人主动单聊推送。

### 1.3 范围界定（v1.11.0）

**包含：**
- 钉钉文档识别 + 读取（三类资源：notable / workbook / doc）
- 看板技能（用户触发 + 定时触发 + 主动提醒）
- 订阅持久化（SQLite）+ 合理默认值
- 看板数据源配置（配置化，不硬编码）

**不包含（后续版本）：**
- 企业知识库的部门级隔离（属 v2.0 多中心权限，与本次无关）
- 生产日报文件类数据源（方法论文档建议长期迁 AI表格，本轮优先做 AI表格 + 钉钉文档两类）

## 2. 核心需求与交互设计

### 2.1 两条交互原则（本次讨论定稿）

| 场景 | 交互策略 | 理由 |
|------|---------|------|
| **学习/入库** | **主动询问确认**：识别文档后主动提示是否入库，本人回复「帮我学习」确认后才入库（当前无审核环节） | 知识入库是不可逆的持久化操作，需本人确认 |
| **每日推送** | **用户主动提出 → 反问细节确认**：频率（每日/每周几/一周多次）、时间、数据源、接收人，确认后才注册。用户上传文档后**只问学习、绝不推销推送** | 推送是打扰性操作，提案必须由用户发起；细节必须确认避免误解 |

### 2.2 场景一：用户发送钉钉文档给小助手

```
用户：[发送 3 个钉钉文档链接]
小助手：📑 已识别 3 份钉钉文档：
  · 研发项目现况表（AI表格，33周，7条记录）
  · 整机测试问题（AI表格，142台）
  · 生产日报（在线表格 .axls）
  👌 回复「帮我学习」可将文档内容入库知识库。
  （← 只提学习，绝口不提推送）
```

> 识别阶段只**登记候选** + 主动提示「是否学习入库」。**不推销推送**——推送由用户自己提出。若用户之后主动说「推送」，再进入场景二。

### 2.3 场景二：用户请求每日推送

```
用户：帮我根据以上几个文件每周一和周五给我推送最新消息
小助手：收到！确认一下推送细节 📋
  ⏰ 频率：每周一、周五，对吗？
  🕘 时间：默认 09:00 可以吗？
  📊 数据源：3 份全部？
  👤 推送给：您本人？
  （确认后）✅ 已设置，立即推一份样例验证格式。
```

> 关键：**推送由用户主动提出**（我们不引导）；提出后**反问确认细节**（频率/时间/数据源/接收人），确认才注册。频率不必是每日——每周几、一周多次都由用户定。无用户显式订阅**绝不主动推送**（主动外发内容底线）。

### 2.4 合理默认值（不反问的前提）

| 缺省项 | 默认值 | 修改方式 |
|--------|--------|---------|
| 推送频率 | 每日 | 反问确认时询问；「改看板频率到每周一三」 |
| 推送时间 | 09:00 | 「改看板时间到 10 点」 |
| 推送接收人 | 发起人本人 | 「也推给XX」 |
| 数据源 | 用户所指的全部文档 | 对话中增减 |
| 提醒模式 | `changes_only`（仅变化时提醒） | 配置项 |

### 3.2 看板 vs 企业知识库隔离（三层）

| 维度 | 企业知识库（现有） | 看板（新增） |
|------|------------------|-------------|
| 数据形态 | 文件 → 切片 → 向量化 | 实时记录 → 临时组装展示 |
| 存储位置 | Chroma 持久化，可回溯 | **不进 Chroma**，每次实时拉取 |
| 数据来源 | 员工发文件 → 入库 | 钉钉 AI表格 / 钉钉文档实时 API |
| 使用方式 | 全员共享查询 | 按**订阅**推给指定人 |
| 生命周期 | 长期，随文件更新 | 即时快照，每日重建 |

- **数据层隔离**：看板数据源走 `dingtalk_doc_client` 实时拉取，物理不进 Chroma。
- **配置层隔离**：看板订阅存独立 SQLite 表 `dashboard_subscriptions`，按订阅人维度管理。
- **权限层隔离**：复用 `check_permission(user, action)`，新增 `dashboard.manage` 等 action；订阅制天然按人隔离，不依赖组织架构。

### 3.3 文件来源两条通道（显式分离）

| 通道 | 去向 | 生命周期 | 代表 |
|------|------|---------|------|
| **企业知识库通道** | 文档「帮我学习」→ doc_mgr → Chroma | 持久化，全员可查 | 标准/故障/经验库 |
| **看板实时通道** | 钉钉文档/AI表格 → 每次 API 实时拉取 | **不入库**，随取随用 | 研发项目现况表、测试问题 |

数据源配置统一带 `source` / `kind` 维度，代码上两条通道各自独立，互不混入。

## 4. 钉钉文档接入设计（核心新能力）

### 4.1 三类资源识别

用户在钉钉单聊发送文档，Stream 收到的是 `alidocs.dingtalk.com` 链接（或文档卡片）。识别流程：

```
链接 → 提取 nodeId（= base_id） → 类型探测 → 对应 API 读取
   ├─ notable（AI表格/多维表）  → /v1.0/notable/bases/{base}/sheets/{sheet}/records/list
   ├─ workbook（.axls 在线表格）→ workbook 接口读 sheet/range
   └─ doc（普通文档）           → doc 接口读内容
```

> 探测方式：优先看 URL 特征（`/i/nodes/<nodeId>` + `sheet=` 参数 → 表格）；拿不准时先按 doc 读，返回「目标节点是 .axls / notable」错误即切换（钉钉官方 doc_key 机制）。

### 4.2 客户端设计 `scripts/dingtalk_doc_client.py`

```
class DingTalkDocClient:
    认证:   复用 DingTalkNotifier 的 token 逻辑（appKey/appSecret → accessToken，
            线程锁 + 提前60s刷新），建议抽取公共 token 管理器
    HTTP:   requests.Session, trust_env=False（同现有，防 Clash 劫持）
    参数:   operatorId（用户 unionId，必填）
    方法:
      parse_doc_url(url)                  → {node_id, sheet_id, kind}
      read_notable_records(base, sheet)   → list[dict]（maxResults≤100 + nextToken 分页）
      read_workbook_sheet(base, ...)      → 单元格矩阵
      read_doc_content(node_id)           → 文本/Markdown
```

### 4.3 认证与权限（关键技术前置）

- **operatorId = 用户 unionId**（跨组织唯一）。项目现有体系用 staff_id / userId（组织内唯一）。
- 需新增 **userId → unionId 查询**：通讯录接口（contact_api 或 `/v1.0/contact/users/{userId}`）返回 unionid，按需缓存。
- 权限开通：`Document.Notable.Read`（AI表格读）+ 文档读取权限，开放平台 → 权限管理开通后**发布应用**。
- 应用可见范围需包含目标文档访问者；操作者本人需对文档有访问权限。

### 4.4 API 端点清单（待实测确认版本）

| 用途 | 端点 | 备注 |
|------|------|------|
| AI表格记录列表 | `POST /v1.0/notable/bases/{base}/sheets/{sheet}/records/list` | maxResults≤100 + nextToken；⚠️ 方法论文档写的 `/v1.0/aitable/...`（GET）为旧版，需实测走哪版 |
| 获取 access token | `POST /v1.0/oauth2/accessToken` | 复用现有 |

## 5. 看板核心子系统设计

### 5.1 数据源配置结构（配置化，不硬编码）

基于方法论文档字段映射，新增 `source` / `kind` 维度：

```yaml
数据源:
  project_status:                 # 研发项目现况表
    source: dingtalk_doc          # aitable | dingtalk_doc | xlsx_file
    kind: notable
    base_id: "np9z..."            # 从文档链接 nodeId 提取
    table_mode: latest_week       # 按周命名分表自动取最新
    field_map:
      "01ZM8y7": {label: 项目名称, type: list_name}
      "YQnOvE5": {label: 状态,     type: dict_name}
    status_groups:                # 排序/关注分组（可配置）
      attention: [滞后]
      normal:    [正常]
  test_issues:                    # 整机下线测试问题
    source: dingtalk_doc
    kind: notable
    base_id: "ndMj..."
    table_mode: fixed
    table_id: "atLkTeV"
    status_groups:
      attention: [故障, 待验证]
      normal:    [已完成, 已打包]

推送配置:
  push_hour: 9
  push_minute: 0
  alert_mode: changes_only        # always | changes_only | off
  title: "恩特能源每日项目看板"
```

### 5.2 核心逻辑（规则采集 + LLM 组装双层）

**第一层 · 规则采集/解析（复用方法论文档算法，确定性）**
- `extract_cell_value(cell)`：None/str/dict/list 通用单元格解析 → 字符串
- `find_latest_week_table(tables)`：正则取数字最大分表（"33周" → 33）
- 解析统计：项目按状态分组、测试问题按状态计数 + 关注 SN 列表

**第二层 · LLM 组装/判断（定时与对话均走 LLM）**
- 把采集到的结构化数据 + 工具列表（含 search_knowledge_base 等）交给 DeepSeek
- LLM 判断：状态置顶排序、识别关注项、**需要时自动调知识库工具结合企业知识库解释卡点/风险**
- LLM 生成看板 Markdown，用固定模板兜底校验（防格式漂移）
- 格式约束保底：钉钉不支持表格语法；总量 ≤5000 字符；长字段截断 200 字；良率小数→百分比；`#DIV/0!`→"无数据"

**推送**：`DingTalkNotifier().send_markdown_to_users(user_ids, title, text)`，单次上限 20 人

### 5.3 订阅持久化（SQLite）

新表 `dashboard_subscriptions`：

```
id | owner_user_id | data_sources(JSON) | push_hour | push_minute |
    alert_mode | recipients(JSON) | created_at | enabled
```

对话指令（"改看板时间""停掉看板"）直接读写此表，重启不丢。

### 5.4 三种触发路径

```
① 用户触发（同步）: 钉钉消息 → get_matched_skill() → 看板技能 match() 命中
                     → handle(): 反问确认细节 → 注册订阅 → 立即推样例（LLM 组装）
② 定时触发（异步）: 独立 BackgroundScheduler cron 到点 → 规则采集 → **LLM 组装/判断**
                     （LLM 结合知识库工具生成看板）→ 推送。不经技能 match，但走 LLM
③ 主动提醒（异步）: 定时采集 + LLM 判断是否有值得关注的变化 → 有则推送提醒，
                     全部正常则静默（changes_only 模式）
```

## 6. 技能化设计

### 6.1 看板技能 `scripts/skills/dashboard.py`

```python
@register
class DashboardSkill(BaseSkill):
    name = "看板"
    description = "每日项目看板：采集钉钉文档数据源，定时或按需推送"
    priority = 80          # 高于 RAG agent(50)，低于 pcb_calc(90) / error_query(100)

    @classmethod
    def match(cls, query) -> bool:
        # 触发词: 看板/推送看板/每日看板/项目看板 + 订阅管理指令（改看板时间/停掉看板）
        # 否定词防误触: 文档/方案/方法论 等词命中则不拦截
    @classmethod
    def handle(cls, query, user_id, **kwargs) -> dict:
        # 用户主动要求推送 → 反问确认（频率/时间/数据源/接收人）→ 注册订阅 → 推样例
        # 或执行改频率/改时间/停推等订阅管理指令
```

## 10. 风险与前置

| 风险 | 应对 |
|------|------|
| 钉钉文档 API 接口版本不明（notable vs 旧版 aitable） | 第 2 步先实测，用真实文档打通一条最小链路 |
| unionId 获取依赖通讯录权限 | 若现有权限不足，需补充通讯录读取范围 |
| 权限开通 + 应用发版需审批 | 尽早发起（外部流程） |
| operatorId 必须对文档有访问权限 | 文档权限由业务方在钉钉侧配置 |
| 定时主动推送有打扰风险 | `changes_only` 默认只推有变化；无订阅绝不主动 |
| 定时走 LLM 生成看板，输出格式可能漂移 | LLM 生成后固定模板兜底校验；关键板块模板化 |
| 钉钉主动单聊消息有每日配额限制 | 监控推送成功率、失败重试；控制订阅人数与频率 |
