# 一、项目概述
## 1.1 背景
恩特能源（天津恩特能源科技有限公司）是一家专注于第三代半导体变流技术的硬科技企业，核心产品是「刀锋」系列全碳化硅储能变流器（PCS）。在 PCS 设备的售后运维中，故障代码查询是一个高频刚需场景：设备报出故障代码后，现场人员需要快速定位故障原因。传统方式依赖翻手册或电话求助，效率低、信息分散。

为了解决这一问题，我们启动了「恩特小助手」项目——一个基于 RAG（检索增强生成）架构的故障代码智能查询机器人，让现场人员通过钉钉群聊就能秒级查到故障原因。

## 1.2 三步走计划
本项目是恩特能源「AI Agent 全生命周期管理平台」长远规划的第一步：

|  | 目标 | 状态 |
| --- | --- | --- |
| 第一步 | 故障代码智能查询系统（MVP→V2） | ✅ 已完成 |
| 第二步 | 扩展技能：经验查询、钉钉知识库等 | ⏳ 规划中 |
| 第三步 | AI Agent 全生命周期管理平台 | 📋 远期规划 |

# 二、系统架构
## 2.1 整体架构
恩特小助手采用「统一入口 + 多技能模块」的架构。所有用户请求统一进入 FastAPI 服务，由入口路由根据意图分发给不同的技能模块处理。

┌─ 用户入口 ─────────────────────────┐ │  Web 页面 (localhost:8000)  钉钉群 @机器人  │ └──────────────┬───────────────────────┘                ▼ ┌──────────────────────────────────────┐ │          FastAPI 服务 (main.py)        │ │         意图路由判定（_is_fault_related）  │ │           │              │              │ │    故障相关          其他（聊天托底）    │ │           ▼              ▼              │ │   error_query        chat               │ │   ┌────────┐     ┌────────┐            │ │   │Chroma  │     │DeepSeek│            │ │   │向量搜索 │     │ 对话   │            │ │   └────────┘     └────────┘            │ └──────────────────────────────────────┘

## 2.2 核心组件清单
| 组件 | 技术选型 | 职责 |
| --- | --- | --- |
| Web 框架 | FastAPI + uvicorn | HTTP 服务，提供 Web 页面和 API |
| 钉钉集成 | dingtalk-stream SDK | Stream 模式，WebSocket 长连接 |
| 向量数据库 | Chroma（持久化） | 存储和检索故障代码向量 |
| Embedding 模型 | BAAI/bge-small-zh-v1.5 | 将中文文本转为向量（CPU 运行） |
| LLM | DeepSeek API (deepseek-chat) | 关键词提取 + 通用聊天 |
| 数据源 | PCS参数表 V1.6.2.xlsx | Excel 存储 133 条故障记录 |
| 同步工具 | sync_kb.py | Excel → Chroma 重建同步 |
| 运行环境 | Python 3.10+, Windows 11 | 当前部署在本地开发机 |

## 2.3 数据流
用户查询的完整数据流：

  ① 用户输入 → ② main.py 意图路由判定
     ├─ 含故障代码或故障关键词 → 进入 error_query
     └─ 其他 → 进入 chat（通用聊天）

  error_query 内部：
    ③ 提取故障代码（如 d4-1）→ ④ Chroma metadata 精确匹配 → ⑤ 返回格式化结果
    ③' 无故障代码 → ④' 判断是否为复杂自然语言
        ├─ 是 → DeepSeek 提取关键词 → Chroma 语义搜索
        └─ 否 → 直接 Chroma 语义搜索
    ⑤ 格式化结果 → ⑥ 返回给用户

# 三、核心模块详解
## 3.1 入口路由（main.py）
### 意图判定策略
main.py 负责接收所有用户请求，并通过 _is_fault_related() 函数判定走哪个技能模块。判定逻辑分为三个优先级：

| 优先级 | 条件 | 路由目标 |
| --- | --- | --- |
| 高 | 匹配到故障代码（正则 d4-1 等） | error_query |
| 中 | 包含故障关键词（故障/报错/异常/告警/停机/急停） | error_query |
| 低 | 其他所有请求（托底） | chat |

关键代码（main.py 第 27~46 行）：

```
_FAULT_CODE_PATTERN = re.compile(r'(d[a-z0-9]+[-~]\d[\d~-]*)', re.IGNORECASE)
_FAULT_KEYWORDS = ["故障","报错","异常","告警","停机","急停"]
_CHAT_TRIGGERS = ["你好","嗨","你是谁","谢谢",…]

def _is_fault_related(query: str) -> bool:
    q = query.strip().lower()
    if _FAULT_CODE_PATTERN.search(query):
        return True
    return any(kw in q for kw in _FAULT_KEYWORDS)
```
### 路由策略设计考量
• 故障代码正则优先：只要用户输入了 d4-1 这样的格式，就一定走故障查询，不误判为聊天。
• 关键词兜底：即使没有故障代码，只要包含故障相关词就走故障查询。
• 聊天作为托底：除此之外的所有请求（包括闲聊、问公司信息、问天气等）走通用聊天。
• Web 入口和钉钉入口路由逻辑保持一致的分离判定（避免不同渠道行为不一致）。

## 3.2 故障查询（error_query.py）
这是整个系统的核心模块，实现了两级查询策略。

### 两级查询策略
| 输入类型 | 匹配方式 | 调 LLM？ | 速度 |
| --- | --- | --- | --- |
| d4-1（故障代码） | Chroma metadata 精确匹配 | ❌ | ⚡ 毫秒 |
| 急停告警（名称） | Chroma 语义搜索 | ❌ | ⚡ 毫秒 |
| 外部急停信号闭合（原因） | Chroma 语义搜索 | ❌ | ⚡ 毫秒 |
| 逆变器报错了怎么办（自然语言） | DeepSeek 提取关键词 → 语义搜索 | ✅ 仅提取 | ⚡ 较快 |

### 第 1 关：精确匹配（不调 LLM）
当用户输入中包含故障代码（如 d4-1）时，首先尝试精确匹配。方法是对 Chroma collection 做 metadata 过滤，直接按 fault_code 字段精确查找。由于不经过向量相似度计算，也不调用 LLM，速度在毫秒级。

```
def _exact_match_by_code(fault_code: str) -> dict | None:
    result = collection.get(where={"fault_code": fault_code})
    if result and result.get("metadatas") and result["metadatas"]:
        meta = result["metadatas"][0]
        return {"metadata": meta}
    return None
```
### 第 2 关：语义搜索（模糊匹配）
如果没有匹配到故障代码（或只是用文字描述的），则进入语义搜索。系统会先判断查询是否为复杂自然语言。如果是（包含 NL 特征词，如「怎么回事」「如何」「怎么办」等），则调用 DeepSeek 做轻量级关键词提取；如果不是（如简单的「急停告警」、「硬件」），则直接用原词进行向量搜索。

语义搜索使用 Chroma 的 query 方法，返回 top-5 最相似的结果，每条结果附带距离分数（distances），用于标记匹配度 [高]/[中]。

### LLM 关键词提取
仅当查询为复杂自然语言时（如「我这个逆变器报错了怎么回事」），才调用 DeepSeek API 做关键词提取。

为什么这样做？
• 省钱：LLM 只用在「不得不用」的场景，简单关键词直接走向量搜索
• 省时间：大部分查询（故障代码、简单名称）毫秒级返回
• 用户体验好：复杂描述也能理解意图

DeepSeek 调用参数：

```
model = "deepseek-v4-flash"
temperature = 0.1   # 低温度，确保输出稳定
max_tokens = 100    # 只有提取，不需要长篇输出
system = "你是一个只输出关键词的工具，不要解释，不要多余内容。"
```
### 回复格式化
回复格式的特殊处理：因为钉钉不渲染 Markdown 粗体（**text**），所以统一使用【】中文括号代替 Markdown ** 作为标签标识。

每条结果内的内容行连续编号（1. 2. 3. ...），空行、分隔线（---）、数据来源行不编号。多条语义搜索结果时，每条结果独立从 1 开始编号，并用「────────── 结果 N ──────────」分隔。

## 3.4 钉钉机器人（dingtalk_bot.py）
### Stream 模式原理
与传统 Webhook 模式不同，钉钉 Stream 模式采用「我们主动连钉钉」的架构：

  • 传统 Webhook：需要公网 IP、需要配置防火墙白名单、需要域名和 SSL 证书
  • Stream 模式：我们 PC 主动与钉钉服务器建立 WebSocket 长连接，不要求公网暴露

这就是为什么我们的部署环境中不需要公网 IP 就能上线钉钉机器人。

### 消息处理流程
钉钉消息处理流程：

  ① 钉钉服务器接收到群聊 @消息
  ② 通过 WebSocket 推送到我们的 ChatbotHandler.process()
  ③ 从回调消息中解析出 ChatbotMessage（消息内容、发送者、群信息）
  ④ 调用 error_query.handle() 或 chat.handle() 处理（路由逻辑与 main.py 保持一致）
  ⑤ 使用 reply_markdown() 方法将结果回复到钉钉群

关键注意事项：Handler.process() 是 async def 方法，但 reply_markdown() / reply_text() 是 SDK 提供的同步方法，不能对它们使用 await。我们的代码中已经正确处理了这一区别。

### 部署配置
需要在钉钉开发者后台完成以下步骤：
  ① 创建企业内部应用 → 开启机器人能力
  ② 选择 Stream Mode（而非 Webhook）
  ③ 复制 ClientID + ClientSecret 填入 local_config.py
  ④ 创建版本并发布（管理员可设免审批）
  ⑤ 安装应用到公司组织
  ⑥ 在钉钉群设置中添加机器人

## 4.2 Chroma 向量库
Chroma 是一个轻量级的本地持久化向量数据库，无需额外部署服务。

  • Collection 名称：error_codes
  • 存储路径：knowledge_base/（自动管理）
  • Embedding 模型：BAAI/bge-small-zh-v1.5（国产中文嵌入模型，30MB，CPU 运行）
  • Metadata 字段：fault_code, name, cause, address, bit_address, attribute, data_type, default_value, notes, description, notes2, sheet_name, row_num

## 4.3 同步流程
sync_kb.py 的工作流程：

  ① 读取 Excel 文件 → ② 解析「遥信（DI）」sheet → ③ 清理重建 Chroma collection
  ④ 计算每条记录的向量 → ⑤ 存入 Chroma（含 metadata）→ ⑥ 校验总数

修改 Excel 后运行：python scripts/sync_kb.py

# 六、技术选型与权衡
## FastAPI
Python 生态中轻量、高性能的 Web 框架。选择理由：
• 原生异步支持，适合 I/O 密集型场景
• 自动 OpenAPI 文档，方便调试
• 启动快、配置少、适合小项目
• 对比 Flask 性能更好，对比 Django 更轻量

## Chroma 向量数据库
选择理由：
• 本地持久化，无需额外部署服务（对比 Pinecone 需要云端）
• 零配置启动，适合小规模（133 条）场景
• 支持 metadata 过滤，实现精确匹配
• 社区活跃，Python SDK 完善
• 对比 FAISS：FAISS 更底层，没有内置持久化和 metadata 过滤

## BAAI/bge-small-zh-v1.5（Embedding 模型）
选择理由：
• 国产中文优化，对中文语义理解好
• 模型仅 30MB，CPU 即可运行，不需要 GPU
• 推理速度快，毫秒级完成
• 对比 text-embedding-ada-002：免费、本地运行、数据不出域

## DeepSeek API
选择理由：
• 性价比高，deepseek-chat 价格远低于 GPT-4
• 国产模型，中文能力强
• API 兼容 OpenAI 格式，迁移成本低
• 仅用于关键词提取和聊天，用量极小

## LLM 仅做关键词提取（不直接做问答）
这是关键的设计决策：
• 省钱：关键词提取每次仅需 100 token 左右，成本可忽略
• 省时间：向量搜索比 LLM 推理快 10~100 倍
• 可靠性：精确匹配和向量搜索结果确定，没有 LLM 幻觉
• 边界清晰：结构化数据用检索，非结构化对话用生成

只有在「复杂自然语言」场景才调用 LLM，简单关键词和精确代码完全不依赖 LLM。

# 七、已知问题与改进方向
## 7.1 当前局限
- 服务可靠性：运行在本地开发机，息屏/睡眠会断开钉钉连接，无法 7×24 小时在线。
- 数据覆盖范围：目前仅覆盖 PCS 参数表遥信（DI）sheet 的 133 条记录，其他 sheet 尚未对接。
- 短关键词搜索：极短关键词（如 2 字以下）语义搜索效果不理想。
- Windows 编码：Windows 控制台 GBK 编码可能无法正常输出 emoji。
- 单一 Embedding 模型：没有对比测试其他模型的检索效果。
## 7.2 后续规划
云服务器部署：

解决 7×24 小时在线问题，建议使用轻量云服务器（如阿里云 ECS）

补充其他 sheet：

将 PCS 参数表其他 sheet（遥测、遥调、遥控等）同步加入知识库

经验查询：

接入项目现场经验文档，支持搜索历史故障处理经验

钉钉知识库集成：

对接钉钉知识库，支持搜索企业内部的文档

短关键词优化：

引入 n-gram 或者同义词扩展，提升短关键词的搜索效果

多 Embedding 对比：

在现有数据上对比 bge-base / m3e / text2vec 等模型的检索准确率
