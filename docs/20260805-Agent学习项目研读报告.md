### 2.2 核心章节要点

**chapter4 — 三种 Agent 循环范式**
- ReAct（4.2）：Thought→Action→Observation 循环，配套 ToolExecutor（注册/取用/格式化工具描述）+ 正则解析器。恩特 `agent.py` 就是这个思路，但用原生 Function Calling（比正则鲁棒）。学习点：4.2.4 调试技巧（打印完整 prompt、分析原始输出、验证工具输入输出格式、few-shot 引导、temperature=0）。
- Plan-and-Solve（4.3）：先规划（Planner 输出 Python 列表）后执行（Executor 带状态）。恩特是纯 ReAct 无显式规划层。
- Reflection（4.4）：执行→反思→优化迭代 + 短期记忆。4.4.5 成本收益分析（迭代≥2 次额外调用，适合质量敏感任务）。

**chapter7 — 自建框架与工具系统**
- 7.1.2「万物皆为工具」：Memory/RAG/MCP 都抽象成工具。
- 7.5.1 ToolRegistry：与恩特 `scripts/tools/__init__.py` 的 `@register` 几乎同构，但多了 `ToolParameter` + `to_openai_schema()` 自动生成 function calling schema —— 恩特现在每个工具手写 DEFINITION dict。
- 7.5.4 工具链（ToolChain）与异步执行器（AsyncToolExecutor）：恩特没有多工具链式编排和并行工具执行。

**chapter8 — 记忆与检索**
- 8.2 四层记忆：Working（TTL）/ Episodic（SQLite+向量）/ Semantic（向量+图谱）/ Perceptual（多模态），每种带 importance 评分（0-1）+「相似度×时间衰减×重要性」检索打分。恩特记忆是短期窗口 + LLM 压缩长期事实，压缩机制更先进，但缺 importance/TTL/forget/consolidate 分层。
- 8.3 RAG 流水线：MarkItDown 统一转 Markdown → 标题层次感知分块 → 统一嵌入（恩特 doc_mgr 几乎一样）。
- **8.3.5 高级检索：MQE（多查询扩展）+ HyDE（假设文档嵌入）** —— 恩特缺失且最值得补，查询侧原样是短板。

**chapter9 — 上下文工程（恩特最大空白）**
- 9.3 ContextBuilder 的 GSSC 流水线（Gather-Select-Structure-Compress）：把系统指令/记忆/RAG/对话历史统一成 ContextPacket，用「相关性×权重 + 新近性×权重」打分，token 预算内贪心选择，`reserve_ratio` 保护系统指令，超限压缩。`_count_tokens` 中文 1 字≈1 token。
- 9.2.1 最小可行工具集（MVTS）：「工具描述臃肿导致选错工具」直接命中恩特工具越加越多的问题。
- 9.4 NoteTool（Markdown+YAML 结构化笔记）、9.5 TerminalTool（白名单+沙箱+超时）：恩特没有。

**chapter12 — 智能体性能评估**
- 12.2 BFCL：工具调用能力评估，AST 匹配校验「函数名+参数」。恩特 166 项 unittest 全是函数级，没测「Agent 循环选对工具、填对参数」。
- 12.4 LLM Judge / Win Rate：LLM 多维度打分、成对对比胜率。恩特 `eval_rag.py` 只测检索层，不测最终回答质量。

### 3.2 核心章节要点

**第2章 — 上下文工程（恩特所有 prompt/记忆/状态问题的理论源头）**
- **KV Cache 三条铁律**：静态前缀不变、动态信息追加末尾、用标准 API 格式。恩特把「当前用户信息 + 最近对话 + 长期记忆」全部拼进 system prompt（前缀）——正是书中点名的反模式（动态注入破坏前缀缓存），且每次请求前缀都变。对「省 token、秒回」诉求，这条最值得改。
- **Agent 状态栏**（实验 2-8 system-hint）：工具调用计数、时间戳、TODO、详细错误信息。恩特循环无任何状态感知（LLM 不知道「已搜几次、第几轮、还剩几轮」）。
- **上下文压缩策略**（实验 2-9 六策略）：恩特完全不压缩工具结果/轨迹，长工具输出反复占上下文。书中「上下文感知压缩」能降 token 75%。
- **提示工程消融**（实验 2-4）：信息组织混乱让任务成功率降 30%+。

**第3章 — 用户记忆和知识库（与恩特 RAG 几乎一一对应）**
- **三层记忆评估框架**（实验 3-1）：基础回忆→多会话检索→主动服务，给「经验库/记忆/知识库」立标尺。
- **双层记忆架构**：少量关键事实结构化常驻 + 原始对话/文档按需检索。恩特的「facts/summary 常驻 + 知识库检索」正是此结构，但缺第三层「上下文感知检索」（实验 3-11），分块是「孤儿块」。
- **混合检索 + 重排流水线**（实验 3-6）：恩特已实现；书中给了离线 evaluate.py 评测法（recall@k/MRR），恩特有 eval_rag.py 但规模小。
- **知识库治理**：版本化、失效过滤、按权限检索。恩特 doc_mgr 做了版本替换，但**检索层没做「失效内容过滤」**（旧版标准可能新旧并召回）。

**第6章 — Agent 评估**
- Rubric 四准则 + LLM-as-a-Judge（实验 6-3）：幻觉否决项、必要/重要/可选项加权。恩特要上线「经验库质量审核/知识库纠错」，这就是评审脚本模板。
- 检索质量三指标 recall@k / MRR / nDCG：恩特 eval_rag.py 已用，但未纳入 CI。
- **Pass@k vs Pass^k**：能力上限 vs 稳定性。恩特 166 个 unittest 是确定性测试，LLM 行为回归测试缺失。
- 成本分析（实验 6-8）：稳定前缀 + 压缩 2×2 对照，恩特「省 token」没有量化依据。

**第4章 — 工具**
- 工具描述「反例」与边界：恩特 4 个工具的 DEFINITION 已有反例，达标。差距在**参数示例**（书中：示例能把工具调用准确率 72%→90%）——calc_pcb_trace 有示例，其余偏薄。
- 工具粒度：恩特缺**通用计算器/代码解释器**兜底复杂计算（可考虑受限 calc 工具）。
- 执行-验证-反馈闭环（实验 4-2）：写文件后自动跑 linter 返回结构化错误。恩特 doc_mgr 入库后无「质量自检」。

## 四、⚠️ 不适用清单（恩特轻量本地部署，避免盲目模仿）

来自 ai-agent-book 明确警告，恩特是「轻量、秒回、省 token、本地化」定位，以下重型做法**不要**模仿：

1. **第7章模型后训练**（SFT/RL 全需 GPU）→ 恩特知识更新走「外部产物」路线（更新知识库/prompt/工具），不走「模型参数」路线。
2. **重型评估环境**（τ²-bench / AndroidWorld / OSWorld / GAIA 全量）→ 为验证 Agent 方法论设计，恩特只要几十条领域问答评估集。书中 GAIA 精选 466 题就是为控成本。
3. **多 Agent 事件驱动架构**（async agent / 事件总线 / Redis Pub-Sub / RabbitMQ）→ 恩特是钉钉单聊同步形态，过度设计。
4. **Coding Agent 全套**（grep/glob/bash/write/edit、沙盒、持久终端、代码解释器沙箱）→ 恩特工具全是只读检索+纯公式，引入代码执行反而扩大攻击面。最多加一个「无网络、纯 math/unit」的受限 calc 工具兜底。
5. **GraphRAG/RAPTOR 结构化索引** → 书中判断标准：「查询主要是找到包含某信息的文档片段，混合检索就够了」。恩特 133 故障+4278 标准切块、查询以「某故障/某标准条款」为主，不需要图谱/树索引，LLM 调用成本也不划算。
6. **Advanced JSON Cards 全套记忆格式** → 书中明确其代价是「每次会话后维护调用明显更贵更慢」。恩特「facts + summary」轻量格式在「大量且非关键」场景下是对的，只需补「冲突覆盖」+「检索细节」。
7. **消融/AB 实验产线基础设施**（GrowthBook 实验平台、AB 测试）→ 恩特用「每工具一个开关 + 手动消融脚本」即可。
