## 二、RAG-STARTER — 「把 RAG 讲明白」的教科书

**位置**：`D:\RAG-STARTER`（FastAPI + SQLite + OpenAI embedding + LLM）

### 架构数据流
```
入库：POST /documents/add → 空格分词切块（200词/40词overlap）→ 调 OpenAI embedding → 存 SQLite（JSON 向量）
问答：POST /chat/ask → 全表读所有 chunk → query embedding → 暴力余弦 Top-3 → 拼 prompt → LLM 回答
```

### 值得学的干净之处
1. **分层极清晰**：api / pipeline / storage / models 四层，一个文件一个职责，30 行讲清一层
2. **零依赖讲透核心算法**：手写 `cosine_similarity`，裸 httpx 调 API，不靠黑盒 SDK
3. **防幻觉 prompt**：system prompt 强制「上下文里没有就说没找到」——RAG 生成端最重要的原则
4. **响应带回 context**：回答 + 检索上下文一起返回，调用方可审计「它到底基于什么答的」
5. **幂等入库**：同 document_id 先删后插，天然覆盖

### 局限（恩特别学）
- 全表暴力扫描 O(N)，数据过几百条就退化
- **空格分词对中文直接失效**
- 无重排/无混合检索/无评估
- embedding 串行远程调用、无缓存
- `.env` 装了 python-dotenv 却从没 `import`——**文档与代码脱节**的典型

### 对恩特的价值
恩特在每一项技术选型上都已经超过它。真正能带走的是三个**思路**：grounding 约束、检索可观测性（返回命中的 chunk + 分数）、检索质量要量化评测。

## 三、industrial-general-rag — 中文工业场景的进阶模板

**位置**：`D:\industrial-general-rag`（BGE-M3 + Milvus + BGE-Reranker + RAGAS + Chroma）

### 核心架构：三级漏斗逐级降级
```
query → ① FAQ 引擎：BM25 匹配高频问答（softmax 阈值 0.85，命中秒答不调 LLM）
      → ② 意图分类：微调 BERT 分「通用知识/专业咨询」→ 通用直接 LLM 答
      → ③ 策略选择：LLM 动态选 HyDE/子查询/回溯问题/直接检索
      → ④ BGE-M3 混合检索（dense+sparse，WeightedRanker 0.7/1.0 融合）
      → ⑤ 子块→父块回捞去重 → BGE-Reranker 精排取 Top-5
      → ⑥ prompt 增强 → LLM 流式生成（WebSocket）
```

### 最值得学的三件事
1. **BGE-M3 混合检索**：一个模型同时出 dense（1024维）+ sparse 双向量，Milvus 建双索引，`WeightedRanker(0.7, 1.0)` 融合——**稀疏权重给得比稠密还高**（工业场景关键词+权重更关键）
2. **父子块两层**：子块 300 字/父块 1200 字，子块保证检索精度、按 parent_id 回捞父块保证上下文完整
3. **完整降级兜底链**：FAQ→RAG→客服话术三级兜底；LLM 失败统一返回客服电话；每个检索策略异常都有「原始 query 直接检索」兜底
4. **RAGAS 评估闭环**：4 指标（Faithfulness/AnswerRelevancy/ContextPrecision/ContextRecall）离线跑，转 DataFrame 落盘
5. **Redis 三层缓存**：BM25 词库缓存 + 精确问答对缓存（TTL 24h）

### 它暴露的坑（恩特别踩）
- **rerank 无绝对阈值过滤**（代码 TODO 自认）：完全无关文档也可能进 Top-5
- **评估集仅 12 条**，离线手工跑，没到自动化闭环
- **密钥硬编码**：.env 明文 API key + docker-compose 明文 key
- 文档加载缺 Excel 处理（恩特 PCS 参数表是 Excel，已有 excel.py 覆盖）
- 调试残留（print、旧代码新旧并存）

### 与恩特的差异结论
它是「重检索、重模型、重依赖」路线，恩特是「精确快通道 + 轻量语义」路线。**恩特抄它的「检索质量增强」骨架（稀疏补充、重排、缓存、评估），保持自己的版本管理、MinerU OCR、精确快通道优势**，不必整仓迁移。

## 四、RAGFlow — 工业级 RAG 引擎的完整样板

**位置**：`D:\ragflow`（Quart + Python/Go 双栈 + ES/Infinity + Redis + React）

### 整体架构
```
web (React + nginx) → api (Quart) → rag 检索核心 + deepdoc 文档理解 + agent 编排
  api: Blueprint 自动注册 30+ 路由；auth 三通道（session/JWT/APIToken）
  rag: 检索核心（search/advanced_rag/graphrag）
  deepdoc: 深度文档理解（parser + vision）
  worker: 独立进程消费 Redis Stream 任务队列
```

### 四大精华

**1. 深度文档理解（deepdoc）**
- 版面识别（LayoutLMv3，分类 Text/Title/Figure/Table 等 10 类区域）
- 表格结构识别（TSR 转 HTML 表格）
- 三种乱码检测识别「有字实无」的影印件，强制 OCR
- 表格图自动旋转 0/90/180/270° 按置信度选优
- Excel 每行转「列名：值; 列名：值」句子
- 图/表用 VLM 生成语义描述

**2. 混合检索 + 引用溯源**
- 一次查询同时下发 BM25 全文（MatchTextExpr）+ 稠密向量（MatchDenseExpr）+ 融合（FusionExpr）三种表达式
- 存储抽象 DocStoreConnection ABC，适配 ES/OpenSearch/Infinity/OceanBase 四引擎
- 重排：外部 Rerank 模型优先，否则本地 KNN 二次调用合并
- **引用溯源**：把答案按句切开，对每句用 embedding 与 chunk 做相似度（词 0.1 + 向量 0.9），阈值 0.63 递减，命中回插 `[ID:n]` 标记，前端可溯源

**3. GraphRAG**
- 每个文档 LLM 抽实体+关系 → 合并全局 networkx 图 → pagerank → 实体消解 → Leiden 社区检测 → 生成社区报告
- 图查询：query rewrite → 三路检索实体 → n-hop 路径扩散 → sim × pagerank 排序
- 工程上带 Redis 分布式锁、checkpoint 断点续跑、重试退避

**4. 工程能力**
- 任务队列：Redis Stream 消费组 + 多 worker + 限流（task/embed/minio/kg 分级）+ 取消 + 进度审计
- 断点续跑：普通任务复用同 digest 旧 chunk；GraphRAG 独立 checkpoint
- 多租户：user 即 tenant，KB 按 joined_tenant_ids 隔离
- 缓存：LLM 结果缓存 + embed 缓存 + 单请求 search_cache
- 可观测：langfuse 全链路 + 逐阶段计时 + token 核算 + 操作审计
- 健壮性：LLM 错误分类 + 指数退避 + SSRF 防护 + AES/SM4 加密

### 对恩特的价值
不照搬庞大体系，优先补三个性价比最高的缺口：**混合检索、引用溯源、任务队列化**——恰好能把恩特「故障代码秒回」的优势保留、把「文档检索可信度」提上来。GraphRAG 与 Agentic 编排属第二梯队。

## 六、研读心得（一句话总结）

- **RAG-STARTER**：「讲明白 RAG」的教科书——学它的分层清晰和防幻觉思想，不是学技术选型
- **industrial-general-rag**：「中文工业 RAG 的进阶模板」——学它的混合检索、重排、缓存、评估，但注意它自己的坑
- **RAGFlow**：「生产级 RAG 的完整样板」——学它的检索抽象、引用溯源、任务队列、工程化思维，但不必全套照搬

**三者串起来就是一条清晰的成长路径：先理解原理（RAG-STARTER）→ 再照着进阶模板补能力（industrial）→ 最后向生产级看齐（RAGFlow）。** 恩特小助手就沿着这条线走，每一步都有可对照的成熟实现，不必再闭门造车。
