## 六、结论与建议

### 6.1 判定结论（对照计划 0.2 判定标准）

**不采纳「LLM 全量托管意图分类」，维持「正则秒回 + LLM 只兜复核盲区」的现状混合方案。**

判定依据（两条判定标准均不满足「扩大范围」的条件）：

1. **边界句无显著提升**：计划判定标准是「LLM 对边界句准确率显著提升（如 ≥90%）」。
   实测边界句 10 条：正则 5/10 = **50%**，LLM 也是 5/10 = **50%**——零提升。
   LLM 在「反问放行」（这跟看板功能有什么关系）、「疑问放行」（看板推送是不是要收费）上
   **反向误判成订阅管理**（正则有否定词表正确放行，LLM 反而接住），说明 LLM 分类
   对「该放行的自然语言反话」并不比正则可靠。

2. **延迟差距 3 个数量级 + 重操作误判风险**：
   - 正则 p50=0.01ms（本地 re），LLM p50=0.6s / p95=0.9s / max=1.6s。
   - LLM 误判明细里出现 **重操作语义漂移**：「帮我推个看板」（开通订阅）被判成
     kanban_push（立即推送）、「也推给张工」（改接收人）被判成 kanban_push。
     订阅开通/改人是**写操作**，LLM 一旦判错会让用户收到错误的确认文案甚至误操作——
     这是 LLM 托管相比正则独有的新增风险。
   - 「ENTARBOSS」是精确口令字符串（本地匹配零成本），LLM 判为 chat——口令类
     确定性匹配本就该留在正则，不归 LLM 管。

3. **LLM 总体 91.4% vs 正则 87.1% 的 +4.3% 优势全部来自正则盲区里的**
   「CQC 3310」「把文档学习入库」等个例——这些更适合**直接补正则**（成本为零、秒回），
   而不是把整条意图链交给 LLM。

### 6.2 本次验证暴露的真实正则盲区/bug（v1.12.0 处理结果，与 LLM 托管无关）

| # | 现象 | 根因 | v1.12.0 处理结果 |
|---|---|---|---|
| 1 | 「删除看板订阅」「删掉我的看板」被正则判成 file_cmd | **bot 的「删除学习」正则 `_DELETE_RE`（`^(?:删除\|删掉)\s*(?:学习\s*)?(.+?)$`）抢在技能层之前拦截了含「看板」的删除句**，看板删除意图永远到不了 dashboard 技能 | ✅ **M1 领域互斥让位**（`routing.detect_domains`）：bot 删除/重学分支配让位（defer）前先探测领域，命中 kanban → 不拦截，让位给 dashboard 技能走订阅删除确认流程（测试 `test_judgement_layer` 覆盖） |
| 2 | 「CQC 3310 标准是什么」判成 chat | `STANDARD_ID_PATTERN` 前缀列表无 CQC（库里有 CQC 3310 数据） | ✅ **不补枚举，统一查知识库兜底**（用户拍板：查询标准知识库也属于查知识库）：标准号正则接不住 → 落 agent → LLM 调 `kb_search` 工具 → standards 语义搜索命中（不依赖前缀枚举）。链路已用测试验证（`kb_search("CQC 3310 标准是什么")` 原样 query 入语义搜索命中库中 CQC 数据） |
| 3 | 「看板设置是什么」判成 chat | `_NEGATIVE_RE` 含「是什么」，把查询配置的疑问句误当反话放行 | ✅ **非操作类让位**：查询配置本就是查询（非操作），被否定词放行是**正确的让位** → 落 agent → LLM 调 `query_dashboard` 查询（测试 mock 验证落 agent 不误接订阅管理） |

> 三项均**不补正则枚举**（CQC 前缀/否定词豁免），统一走「让位 + 工具兜底」治本路径——
> 正则秒回快速通道只管确定性意图，接不住的自然语言查询交还 LLM 走查询工具。

> 「项目进展怎么样」「现在就推看板」等实时查看/立即推送场景判为 chat/kanban 是**设计使然**——
> 它们本来就走 agent 兜底 → LLM 调 `query_dashboard` / `push_dashboard` 工具（这正是 0.3 的对接链路），
> 不需要技能层接管。

### 6.3 技能层与 agent 托底工具对接分析（计划 0.3）

- 现状链路：`bot → get_matched_skill(match) → 高优技能 handle（秒回）→ agent 兜底
  （LLM 循环 → function calling 调 10 个注册工具）`。
- 若将来把技能层 match 改为 LLM 意图分类（本次验证已证明暂不可行），链路是：
  分类命中 → 对应技能 `handle` **仍用原确定性处理函数**（秒回不退化）；未命中 → agent 兜底
  → LLM 调工具。**工具调用链完全不变**。
- 技能 handle 与工具的关系（对接示例）：`pcb_calc` 技能 handle 内部复用 `calc_pcb_trace` 工具
  的同源实现；`dashboard` 技能 handle 复用 `dashboard.service`；`agent` 技能内部消费全部 10 个工具。
- **结论**：技能层（路由/处理器）与工具层（LLM 执行）是**两层机制**；即使未来 LLM 托管
  「识别意图」（路由），也不改变「执行」（工具）——这正是「技能 vs 工具」本质区别的体现，
  v1.12.0 的板块化只作用于工具层，技能层保持独立。

### 6.4 给 v1.12.0 的范围建议（结论已落地）

- **不引入 LLM 意图托管**（数据不支持），v1.12.0 只做工具板块化重构 + 判定层治本框架。
- 6.2 的 3 个盲区/bug **已在 v1.12.0 全部处理**：① 领域互斥让位（kanban 删除不被 bot 抢）；
  ②③ 非操作类查询不补枚举，落 agent 走 `kb_search`/`query_dashboard` 工具兜底（链路测试覆盖）。
- 验证脚本 `scripts/validate_intent_llm.py` 保留作后续「正则补强」回归基线（可复跑对比）。
