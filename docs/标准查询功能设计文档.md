## 一、背景与目标

### 1.1 当前状态

恩特小助手目前只覆盖 PCS 故障代码数据（133 条，Excel 来源），通过 Chroma 向量数据库提供精确匹配 + 语义搜索。

### 1.2 本次目标

将储能变流器相关的**行业标准和国家标准**（PDF 格式）纳入知识库，实现：

1. 用户可通过自然语言查询标准内容
2. 标准查询与故障查询互不干扰
3. 精确标注每条数据的标准编号和来源，确保可回溯
4. 后续可扩展到更多类型的标准文档

## 二、数据源分析

### 2.1 现状摸底

`data/standards/` 目录下共有 **9 份 PDF 文件**，经 PyMuPDF 扫描分析：

| 文件 | 页数 | 大小 | 可提取文字 | 类型 |
|------|:---:|:---:|:--------:|:----:|
| 62109光伏发电系统用储能变流器技术规范 | 84 | 2.3MB | 102,097 | 文本PDF |
| CQC光伏发电系统用储能变流器技术规范 | 84 | 2.3MB | 102,097 | 文本PDF |
| EN 62109-1 | 173 | 1.4MB | **0** | 纯扫描图片 |
| EN50178 | 102 | 1.1MB | 326,667 | 文本PDF |
| EN50438_2008 | 54 | 2.6MB | **0** | 纯扫描图片 |
| GBT16935.1-2008 | 58 | 2.4MB | **0** | 纯扫描图片 |
| GB_T_34133-2023 | 49 | 1.7MB | 42,824 | 文本PDF |
| I60664-1E2 | 152 | 1.3MB | 343,573 | 文本PDF |
| 电化学储能系统储能变流器技术要求 GB_T 34120-2023 | 44 | 13MB | **0** | 纯扫描图片 |

**结论：5 份可提取文字，4 份为纯扫描图片，需要 OCR。**

### 2.2 你的担心完全有道理

两份 PDF 看起来是 62109 标准的两个版本（原始版和 CQC 认证版），内容几乎一致。62109这个标准名在「EN 62109-1.pdf」中也出现了，属于是同一个 IEC 标准的不同转化版本。

**PDF 的类型决定了提取质量**，不是所有的 PDF 都可以用简单的文本提取搞定。

## 三、PDF 文本提取方案

### 3.1 文本型 PDF（5 份）

直接用 **PyMuPDF（fitz）** 提取，效果可靠。

```
PDF text layer  →  PyMuPDF.get_text()  →  纯文本
```

- 准确率：接近 100%（PDF 本身的文字层直接读取）
- 风险：目录、页眉页脚等非正文内容会混入
- 处理：入库前做简单清洗（去掉页眉页码，合并段落）

### 3.2 扫描型 PDF（4 份）— 需要 OCR

纯扫描 PDF 本质上是图片集，需要 OCR（光学字符识别）才能提取文字：

```
PDF 图片页  →  OCR 引擎  →  纯文本
```

目前有两条路线：

#### 路线 A：PaddleOCR（推荐 ✅）

```
优点：免费、开源、中文识别效果好、支持中英混排
缺点：首次需下载模型（~100MB）、CPU 上识别较慢（一页 2-5 秒）
安装：pip install paddleocr
```

对 4 份扫描 PDF 的预估处理时间：
- EN 62109-1.pdf（173 页）→ ~6-15 分钟
- EN50438_2008.pdf（54 页）→ ~2-5 分钟
- GBT16935.1-2008.pdf（58 页）→ ~2-5 分钟
- GB_T 34120-2023.pdf（44 页）→ ~2-5 分钟

**注意：OCR 做不到 100% 准确。** 对于标准文档这种严谨内容，可能有千分之几的识别错误（数字混淆、符号错位），需要在搜索结果中标注来源页码，让用户能对照原文。

#### 路线 B：调用云端 OCR API

```
百度云 OCR / 腾讯云 OCR → 按量付费
优点：识别率更高（>99%），速度更快
缺点：要花钱，需要网络
```

#### 路线 C：先用 PaddleOCR 本地识别，后期有预算了上云

**我建议的路线**：先用 PaddleOCR 做本地识别跑通功能，标注「OCR 识别可能存在误差，请对照原文」，后续优化再考虑上云。先跑通，再优化。

### 3.3 精确定位方案

提取到完整文本后，需要做**切块**才能入库（整份 PDF 太长，语义搜索效果差）。

切块策略：

```
整份 PDF 文本
     ↓
按章节/条款切块（正则匹配 "第X章" "X.X" "X." 等模式）
     ↓
每块 = Chroma 中的一条记录
     ↓
metadata 记录标准编号 + 章节号 + 页码
```

示例：

| 记录 | 标准编号 | 章节 | 页码 | 文本片段 |
|------|---------|------|:---:|---------|
| 1 | GB/T 34133-2023 | 第1章 范围 | 1 | 本标准规定了... |
| 2 | GB/T 34133-2023 | 第2章 规范性引用文件 | 1 | 下列文件... |
| 3 | GB/T 34133-2023 | 3.1 术语和定义 | 2 | 储能变流器... |
| ... | ... | ... | ... | ... |

这样做的好处：
- 用户搜「并网要求」→ 只返回相关章节，不是整本标准
- 每条结果带来源页码，方便对照原文
- 置信度低的 OCR 内容也能靠页码回溯校验

## 四、架构设计

### 4.1 数据存储

Chroma 中新建一个独立的 collection `standards`，与现有的 `error_codes` 并列：

```
Chroma 向量数据库
  ├── error_codes    → 133 条 PCS 故障记录（现有，不动）
  └── standards      → N 条标准文档切块（新增）
```

### 4.2 standards collection 的 metadata 结构

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `std_id` | string | 标准编号 | `GB/T 34133-2023` |
| `std_title` | string | 标准名称 | `储能变流器检测技术规程` |
| `chapter` | string | 章节号 | `3.1` |
| `chapter_title` | string | 章节标题 | `术语和定义` |
| `page` | int | 起始页码 | `2` |
| `file_name` | string | 来源文件名 | `GB_T_34133-2023.pdf` |
| `confidence` | string | 提取方式 | `text` 或 `ocr` |
| `section_text` | string | 该章节的完整文本 | ... |

### 4.3 同步脚本

新建 `scripts/sync_standards.py`，功能：

```
1. 扫描 data/standards/ 目录下所有 PDF
2. 对每份 PDF：
   a. 尝试 PyMuPDF 提取文字
   b. 提取不到 → 调用 PaddleOCR
3. 按章节/条款切块
4. 写入 Chroma standards collection（增量模式）
5. 输出同步报告（多少份成功、多少份失败）
```

### 4.4 Agent 工具设计

在现有 RAG Agent 中新增一个独立工具 `search_standards`：

```python
TOOLS = [
    {
        "name": "search_faults",
        "description": "搜索 PCS 故障代码。当用户问故障代码或报错时使用。包含故障代码的名称、原因、地址等。"
    },
    {
        "name": "search_standards",
        "description": "搜索储能变流器/光伏行业标准。包含国家标准(GB)、国际标准(IEC/EN)等。当用户问标准、规范、技术要求时使用。"
    },
]
```

两个工具各搜各的 collection，LLM 根据问题判断调用哪个。

## 五、用户使用流程（钉钉端）

### 5.1 信息流

```
用户在钉钉发消息
      ↓
钉钉 Stream 接收 → ErrorQueryHandler.process()
      ↓
技能注册中心路由 → RAGAgentSkill（始终匹配，兜底）
      ↓
RAG Agent（LLM + 工具调用）
      ├─ 判断问题意图
      ├─ 与故障相关 → 调 search_faults → error_codes collection
      ├─ 与标准相关 → 调 search_standards → standards collection
      └─ 两者都不相关 → 直接聊天回答
      ↓
LLM 综合搜索结果 + 自身知识 → 组织自然语言回答
      ↓
回复给钉钉用户
```

### 5.2 LLM 判断逻辑

| 用户问题示例 | LLM 应该 | 调用的工具 |
|-------------|---------|:---------:|
| `d4-1 是什么故障` | 搜故障代码 | `search_faults("d4-1")` |
| `并网电压要求是多少` | 搜标准 | `search_standards("并网电压要求")` |
| `GB/T 34133 里怎么检测效率` | 搜标准 | `search_standards("GB/T 34133 效率检测")` |
| `PCS 报外部急停` | 搜故障 | `search_faults("外部急停")` |
| `储能变流器的效率要求是多少` | 搜标准 | `search_standards("储能变流器 效率要求")` |

### 5.3 回答格式

标准查询的结果格式（钉钉 Markdown）：

```
【标准编号】GB/T 34133-2023
【章节】第5章 效率试验
【内容】

（该章节的具体内容摘要）

---
数据来源：GB_T_34133-2023.pdf → 第5章 → 第12页
```

### 5.4 异常处理

| 场景 | 行为 | 回复示例 |
|------|------|---------|
| 搜到了 | 返回内容 + 来源 | 正常回答 |
| 没搜到 | 告诉用户没找到 | "知识库中未找到相关标准，建议：1. 换关键词试试 2. 联系负责人更新标准库" |
| 标准文件有但 OCR 失败 | 记录日志，跳过 | "当前未能处理此标准的全文检索" |
| 用户问的标准不在库里 | 告知范围 | "目前仅收录了储能变流器相关的9份标准，你问的这个暂时没有" |

## 七、风险与应对

| 风险 | 级别 | 应对 |
|------|:----:|------|
| OCR 识别错误导致信息不准确 | 中 | 标注 `confidence` 字段，搜到的内容提示用户对照原文 |
| 标准切块后语义不连贯 | 低 | 切块策略可调：先按大章切，效果不好再调细 |
| PaddleOCR 处理慢（173页的 EN 62109-1） | 中 | 后台异步跑，同步脚本完成后通知 |
| 两份「62109」内容高度相似，搜索可能重复 | 低 | 入库时去重处理，相同标准编号只保留一份 |
