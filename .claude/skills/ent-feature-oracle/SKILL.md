# 恩特功能预言机（Feature Oracle）

老板一句话，落地一张图。输入一个模糊的新功能想法，输出：能力映射 → 分层落地方案 → 天马行空的其他需求 → 风险与版本建议。**设计不实现。**

## 核心原则

1. **永远先读项目，再开脑洞** — 设计前必须读 CLAUDE.md、项目结构、相关子系统代码、TODO.md。脱离现有逻辑的脑洞是空想，标注「成本/收益」让用户判断。
2. **复用优先，新增兜底** — 能复用的现有能力（tools/ 工具注册、知识库注册表、看板子系统、识图、文件接收、Agent 循环、记忆）绝不复刻。脑洞的价值在「用现有积木搭出新玩法」，不在发明新轮子。
3. **天马行空但不失控** — 发散出的相邻需求要标清「值得做/可能有用/纯脑洞」，并给每个附一句成本或依赖，防止用户被脑洞淹没。
4. **版本号只建议，用户拍板** — 遵守 CLAUDE.md 规则 6。

## 必读清单（按需取用，别全读）

- `CLAUDE.md` — 项目概述、组件表、文件类型→Collection 映射、运行方式、协作规则
- `TODO.md` — 现有待办，脑洞别和已有计划打架
- `CHANGELOG.md` — 最近版本亮点，判断「时代在跟谁」
- 相关子系统：`scripts/tools/`（工具注册）、`scripts/skills/`（技能）、`scripts/doc_mgr/`（文档）、`scripts/dashboard/`（看板）、`scripts/kb_registry.py`（知识库注册表）、`scripts/dashboard_scheduler.py`（调度）

## 工作流程

### 1. 澄清需求（先问 3 个问题，答案已知就跳过）
- 谁用？钉钉单聊的哪个角色（员工/主管/老板/管理员）？
- 什么时候用？一次性还是持续（推送/订阅/看板这种要定频率）？
- 数据从哪来？现有数据源（PCS表/标准PDF/钉钉文档/经验库）还是新输入？

把模糊需求写成一句 **EARS 式**：「当 [触发条件] 时，系统将 [行为]，使得 [用户价值]」。这一步把老板的「我想让机器人能X」翻译成可验收的功能点。

### 2. 能力映射（复用盘点）
把需求拆成「能力块」，逐块对照现有系统找「可复用的积木」：

| 需求能力块 | 现有可复用 | 缺口 |
|-----------|-----------|------|
| 接收用户输入 | 钉钉 Stream bot（dingtalk_bot）| — |
| 理解意图/聊天 | Agent 循环（agent.py）+ DeepSeek | — |
| 查知识 | 通用 kb_search（v1.12.0 改名，指定库/全库合并）| — |
| 存知识 | 多知识库注册表 + doc_mgr 入库管道 | — |
| 定时推送 | dashboard_scheduler（订阅/alert_mode）| — |
| 读文档 | dingtalk_doc_client（notable/workbook/doc）| — |
| 识图 | tools/image_describe（qwen，v1.12.0 改名）| — |
| 收文件 | file_handler（uploads 按部门/员工/日期）| — |
| 用户/权限 | SQLite user_store + 五中心 center_config | — |

**核心提问：这个新功能，是「新积木」还是「旧积木的新玩法」？** 90% 的老板需求是后者。

### 3. 分层落地方案（给出每个层级的改动文件 + 改什么）
按项目骨架排实施路径，从底向上：
1. **数据层**：要不要新表（user_store.db / knowledge_bases）/ 新数据源 / 新配置（config.py 开关）
2. **服务层**：新模块放哪（scripts/ 下哪个文件 / tools/ 注册 / skills/ 技能）
3. **接口层**：Web 要不要动（main.py / admin）、钉钉要不要新消息路由
4. **调度层**：要不要定时（dashboard_scheduler 订阅模型可复用）
5. **测试层**：至少 3 个测试（本功能 + 相邻边界 + 旧功能不回归）——遵守 CLAUDE.md 规则 8

### 3.5 原子任务拆解（借鉴 feature-planning 格式）
把分层方案转成**可逐条执行的任务列表**，每一条都能独立开工、验证、交付：
- 每条任务标注 **文件路径:行号**（`scripts/xxx.py:45`，精确到改动点）
- 标 **依赖**（任务 N 完成才能开工）
- 标 **集成点**（这条改动和现有哪个模块衔接，会不会撞路由/抢意图——参考 subscription_commands 教训）
- 每条带 **测试**（本功能用例 + 相邻边界 + 旧功能不回归，遵守 CLAUDE.md 规则 8）
- 写下 2~3 条**架构决策**（为什么这么接，防止未来的人拆栅栏）

### 4. 天马行空（发散其他需求，三层标注）
围绕需求往外扩一圈，逐条标级别：
- **🔴 必带**：没有它功能不完整（如权限/部门可见性、出错兜底、并发保护）
- **🟡 很可能要**：用户用了 3 次就会提（如「能不能也推给XXX」「能不能改成每周」）
- **🟢 纯脑洞**：未来可能，标一句成本/依赖（如「和识图联动」「打通记忆」）

发散时对照项目已有约束挖「天然要带上」的：
- 权限：五中心部门、ENTARBOSS 管理员模式、多用户并发锁
- 成本：LLM 只用在刀刃上（能本地匹配不调 API）、MinerU 每日额度
- 运维：本地电脑息屏断连、版本迁移（SQLite 表变更要迁移）、CHANGELOG 同步
- 体验：钉钉不渲染 Markdown（用【】）、上下文缓存命中率、回复秒回

### 5. 风险与边界
- 误判风险（如果这个功能是自然语言触发，参考 subscription_commands 的正则教训——别用正则硬扛意图，必要时走 LLM 分类）
- LLM 成本（每条推送/每次查询花多少）
- 数据一致性（新表迁移、旧数据兼容）
- 跟现有功能打架的地方（「发文档」已被看板占用，新功能别抢路由）

### 6. 小步实施计划
拆成 2~5 分钟可验证的步骤（遵守用户小步偏好），每步结尾「验证方式」。第一版只做 🔴 必带 + 核心能力，🟡🟢 排后续。

## 纪律
- 只输出方案，不改代码；用户确认后再实施
- 方案里每个「新增」都要先证明「现有确实没有」（不能因为懒而复刻）
- 脑洞标级不标量——🟢 脑洞最多列 3 条，别让发散淹没决策
